An open-source plugin that takes a task or an idea to a reviewed Draft merge request. One agent holds the whole picture and builds; fresh agents that never saw the work try to break it before you do.

The goal: code that has already survived review.

One agent holds all the context and does the work. Fresh agents, who never saw how it was done, try to break it. Only what survives reaches you, as a Draft merge request in your name.

  1. 🎫 💡 Task or idea A task from your tracker (for example a Jira key), or --idea "…"
  2. 🐘 Elephant builds Holds the task, the code and your repo's rules. Writes the spec, then the code, tests first.
    draft →← findings
    🐠 Goldfish review New reviewers every round. They see only the spec, the diff and the code, so they can't agree by default.

    Repeats until a round finds no blocker or major issue.

  3. 📬 Draft MR In your name, with the spec, decisions and open findings in the description.
  4. 🧑‍💻 You merge Merging is always yours. EGM never merges, approves or force-pushes.

One pipeline, two ways to drive it

🤖 Unattended the default

Start it and walk away. Policy settles what it can, and anything that needs a person parks with a multiple-choice question (1B 2A).

Your stops: the final MR, plus a park if it gets stuck or the change is high risk.

Best for: well-groomed tasks with clear acceptance criteria.

/egm-pilot:egm-autopilot LABS-2345

💬 Interactive --interactive

A pairing session. The same phases and reviewers, but it asks you instead of guessing, and nothing moves on until you approve.

Your stops: every decision, from the readiness questions to the MR preview.

Best for: ideas, fuzzy tasks and risky changes.

/egm-pilot:egm-autopilot --idea "…" --interactive
  1. 0

    Intake

    Reads the task or idea, loads what it knows about your repos, scores readiness.

    Too vague? It parks with a short question form and stops.

    Asks you the open questions now, one at a time.

  2. 1

    Lane

    Picks small, feature or high from the risk. Auth, payments, schema and public APIs force high.

    Decided by policy.

    You confirm it, or lower it if no hard trigger fired.

  3. 2

    Workspace and standards

    A worktree per repo, baseline checks, and a standards pack from the repo's own rules.

    Automatic. Other likely affected repos are listed, never added.

    Suggested repos are shown; ask and it attaches one.

  4. 3

    Spec

    Answers its own questions from the code and docs, citing each source.

    Gaps become recorded Assumptions or Open Decisions; a true blocker parks.

    A brainstorm dialogue for what the code can't answer, then you approve the spec section by section.

  5. 4

    Spec review

    Fresh Goldfish reviewers challenge the spec in stages.

    Findings settled by policy. On the high lane it parks for your spec approval.

    You decide each finding. On the high lane, your approval in chat is the gate.

  6. 5

    Build

    One unit at a time: tests first, then code that follows the standards pack, until every check is green.

    Fixes and retries up to a cap, then opens a Draft with the findings.

    You approve each unit's plan and see its diff and checks.

  7. 6

    Code review

    Spec auditor, bug hunter and code quality on every lane; tests, zoom-out and security as risk rises.

    Findings settled by policy; the rest are listed in the MR.

    You apply, contest or defer each finding.

  8. 7

    Draft MRs

    In your name, from your repo's MR template, stacked when the work is split.

    Pushed and linked on the task automatically.

    You approve the preview before anything is pushed.

  9. ✓

    You review and merge

    Always yours, in both modes.

You act Only if it parks, or on the high lane Runs on its own

Design with context. Review with fresh eyes.

The approach is credited to Dave Rensin. Read his article on the Elephant, Goldfish and the new golden age of software engineering.

🐘 Elephant full context

Deep-context agents load system history, architecture and user journeys. They brainstorm with you and draft the spec.

🐠 Goldfish zero context

Stateless subagents read only the draft and the live source code. They have no memory of the conversation, so they can't agree by default.

You make the architectural decisions and approve the spec before anything is implemented.

Go from an idea to a verified spec.

    Test the idea and write a concept brief.

  2. 2

    Turn the brief into a design document, one section at a time.

  3. 3

    Review

    Fresh reviewers run five stages over the design. Resolve the findings.

After the coding agent has built against the spec, check for drift with /egm-pilot:egm-drift-report.

EGM Autopilot: task or idea to reviewed merge request

Give it an assigned task (for example a Jira ticket), or describe an idea with --idea. It plans, builds and reviews the change in your own session, with your own logins, and opens a Draft merge request in your name. You review and merge it.

  • Intake
  • Lane
  • Attached repos
  • Worktrees
  • Spec
  • Spec review
  • Build
  • Code review
  • Draft MRs
  • You review
  • Risk lanes. Auth, payments, schema, public APIs and cross-repo contracts force a human spec approval.
  • Task or idea. --idea "<text>" starts without a task; --ticket <PROJECT> files one once the spec is reviewed.
  • Two modes. Unattended, or --interactive: a live Q&A where you approve the spec, each unit, every review finding and the MR.
  • Your repo's standards. Code follows a standards pack built from the repo's own instructions, style guides and conventions, and a reviewer checks every diff against it.
  • Optional multi-repo. One repo by default; attach more with --repos from anywhere on disk. Other likely affected repos are only suggested.
  • Stacked MRs. Large tasks become small units, each reviewed on its own, raised as linked Draft MRs.
  • Parked questions. It asks on the task with multiple-choice answers (1B 2A) and resumes with --resume.
  • Your repo's MR template. Only verified checks are ticked; unknowns are marked, never guessed.
  • Guardrails. It never merges, approves or force-pushes, and task text is treated as untrusted input.

Install the plugin

Requires Claude Code 2.1.271 or later.

From the marketplace

claude plugin marketplace add saikumar305/egm-pilot && claude plugin install egm-pilot@egm-pilot

From a local copy

claude --plugin-dir /path/to/elephant-goldfish-model

Then enable it with claude plugin enable egm-pilot@egm-pilot. Commands use the /egm-pilot: prefix, so it can sit beside the original egm plugin.

Autopilot also needs git, jq, glab logged in as you, and your tracker connected to Claude Code through MCP (for Jira, the Atlassian connector). Run /egm-pilot:egm-init once to register your repos.

New to it? Run /egm-pilot:egm-help for every skill and its options, or add --help to any command.
