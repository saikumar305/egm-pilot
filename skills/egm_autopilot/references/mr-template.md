# MR template

The MR description is the human's single review surface. Optimize it so a reviewer can decide
in minutes: lead with what needs their judgment, not with a diff recap.

Title: `<KEY>: <ticket summary>` (prefix `[SPEC]` for spec-gate MRs, `Draft:` when attention needed)

```markdown
## Needs your judgment  <!-- omit section if empty -->
- **Open Decisions** (I chose a default and proceeded; veto if wrong)
  1. <decision> -> chose **<default>** because <reason>. Alternatives: <a>, <b>.
- **Spec Deviations** <what changed vs approved spec, why, evidence>
- **Unresolved findings** <finding, severity, why not fixed>

## Summary
<2-4 sentences: what changed and why. Link: <JIRA URL>. Spec: <path or link>.>

## Acceptance-criteria traceability
| # | Acceptance criterion | Spec § | Test(s) | Code |
|---|---|---|---|---|
| 1 | ... | §3.2 | `test_x` | `path/file.py:L10-40` |

## Assumptions (low impact, recorded not asked)
- ...

## Verification
| Check | Result |
|---|---|
| Build / Lint / Typecheck | pass |
| Tests (new / total) | 12 new / 340 pass |
| Secret scan | clean |
| Baseline failures (pre-existing) | none |

## AI review (isolated reviewers)
Rounds: spec <n>, code <n>. Findings: <applied> applied, <decided> decided, <deferred> deferred,
<rejected> rejected (no evidence). Reviewers: egm-code-spec-auditor, egm-code-bug-hunter, egm-test-adequacy[, egm-code-security].

## Follow-ups (out of scope, not implemented)
- <suggested Jira sub-task title and one-line description>

---
Lane: `<small|feature|high>` | Confidence: **<high|medium|low>** (<reasons>) | Run: `<run-id>`
Generated by egm-autopilot. Audit trail: `.egm/runs/<KEY>/`
```

Rules:
- Never claim a check passed unless you ran it in this run and saw the result.
- Quote real file:line references; do not invent them.
- Keep the whole description under ~120 lines; link to the spec instead of pasting it.
